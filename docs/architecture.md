# 架构

请求沿固定分层流动：OpenClaw/网页端 → FastAPI 路由 → Pydantic Schema → Service → SQLAlchemy → SQLite。网页结构化操作可直接进入领域 Service；自然语言和微信写入先经过 proposal 复核。路由负责 HTTP、身份和班级归属，跨表校验、事务、快照、排班、调课与分析位于 Service。

网页班级对话由 FastAPI 完成登录与班级归属校验、附件留存和任务取消，再代理到绑定的 OpenClaw class agent。Gateway 管理凭据不会进入浏览器；网页文字只进入 OpenClaw 会话，不写入 ClassClaw 数据库。班级模型偏好保存在 `class_agent_bindings`：主模型同步到该 Agent runtime，网页图片 turn 使用后端受控模型覆盖，服务端语音识别通过临时录音调用 OpenClaw STT 并在结束后删除录音。

前端 `agentChatStore` 将对话列表和在途请求放在按用户/班级隔离的标签页内存中；页面只订阅状态。创建新对话和站内导航不取消已发送请求，晚到的结果按原始对话对象归位；返回页面恢复消息和忙碌状态。AppShell 导航时调用页面 `dispose()` 释放视图/输入设备资源，明确的“停止”、“删除对话”、登出和超时才取消任务；实际网络断开仍适用后端断开检测。删除只影响指定对话的内存记录及在途请求，迟到结果不能恢复已删除内容。聊天原文不持久化，刷新/关闭标签页后的恢复不在此设计范围内。对话页用“本班专属 Agent”作为标题和无障碍名称，不展示内部 Agent ID。

学生名单默认按学号自然升序（1、2、10），兼容前导零、全角数字、带字母前缀及长学号，原始学号不改写。后端读写连接均注册 `STUDENT_NO` SQLite 排序规则，在分页前排序；Python 汇总与网页未排座学生池使用相同的数字分段规则。数值相同的写法以短写法优先，再按文本及唯一 ID 保证稳定顺序。学生选择器保留该顺序，不按选择频率重排。成绩排名、日期/项目分组、已有座位布局及值日公平性约束保留业务含义，同一优先级下按学号排序；建班编辑表只在载入名单时排序，输入过程中不移动行。

网页回复使用 SSE（旧 JSON 调用仍兼容），公开文本片段持续写回原对话；只有完整终态才标记成功，部分回复中断后明确标注。单轮生产任务和有界片段缓冲仅存在于 HTTP 请求生命周期，不引入离线后台任务、消息队列或新的数据库表。思考强度来自静态班级默认配置或本会话覆盖，后端通过插件的固定鉴权端点设置同一 owner/class/conversation 隔离的 Gateway 会话，不修改 Agent 默认来实现单会话覆盖。

AI 等待与数据库写入分段执行：准备阶段保存附件或结构化任务记录，提交后通过 `app.database.suspend_writer(db)` 归还全局写锁及单写连接；等待 Gateway/语音转写期间不能访问该数据库会话。响应或异常返回时，异步重新取得写锁并失效 ORM 缓存，再进行版本校验、保存结果或错误状态。禁止在存在待提交的 ORM 修改、已 flush 的写入或批量 SQL 写入时进入无锁等待；不能用隐式提交破坏整批事务。取消期间也必须完成锁的恢复，保证后续错误处理和请求清理使用正确的锁。

该边界覆盖网页班级聊天、通用文件/文本提取（建班、课表、座位、学生事件、interaction analysis）、聊天运行配置检查、班级模型配置请求、语音转写和微信二维码等待。Agent 回调的分析/预览/提交因此可以在聊天请求尚未结束时取得写锁。仅修改外部配置或清理 OpenClaw 会话、不写 SQLite 的管理端请求使用读会话完成鉴权。创建/删除 Agent、完整初始化等涉及外部资源与本地状态协调的运维流程仍保留串行边界，不能把整个 Service 任意放进无锁区间。

数据库采用“核心业务库 + 独立用量库”，详见 [数据库拆分](database-splitting.md)。`app/database.py` 只管理核心事实；`app/usage_database.py` 管理独立 `UsageBase`、读池、单写连接和写锁。AI 用量在无业务写锁区间通过线程池写入 `usage.db`，失败只记录告警，不提交或回滚业务会话。账户、审计、工作流与分析缓存仍保留在核心库；统计页面在 Service 层合并两库的查询结果，不使用跨库 JOIN 或事务。

```text
确定性网页字段（班级名称/年级等） ───────────────→ Onboarding 草稿

网页自然语言/粘贴文本/文件 ─→ OpenClaw Responses ─┐
微信消息/附件 ─→ classclaw_analyze_interaction ───┼→ 结构化结果（不保存原文）
OpenClaw 对话式班级引导 ─→ Skill + 受限工具 ──────┘
                                                   │
                                                   ▼
                                       后端 Schema 校验 + Proposal
                                                   │
                                        用户在聊天中一次核对确认
                                                   │
                                                   ▼
                                      固定执行器 + 单事务落库
```

`app/main.py` 注入请求 ID，统一处理业务错误、参数错误和 SQLite busy/locked。`app/api/v1` 按领域拆分路由；`app/services` 实现业务；`app/analytics` 仅基于数据库事实生成结构化指标和证据；`scripts` 提供初始化、种子、备份、恢复和附件维护。

关键边界：没有任意 SQL/Python/URL 执行接口；proposal 只能选择白名单 operation；预览保存归一化 payload、revision 和有效期，确认后由固定执行器完成写入。班主任请求按唯一班级归属隔离。删除学生使用软删除；班级彻底删除先清理外部 Agent 运行配置，再原子清理班级业务数据并保留轻量审计；附件文件名由 UUID 生成；审计不保存整份前后快照。

OpenClaw 插件是传输与工具边界，Skill 是对话和分析流程边界。插件注册读、附件暂存、interaction analysis、proposal 和提交工具，不暴露创建班级/onboarding mutation；提交钩子只注入可信班级范围，不创建额外审批卡。班级专属 agent 的可信 `agentId` 映射为固定 `class_id`。

`interaction_analyses` 保留渠道、外部消息 ID、附件引用、选定班级、OpenClaw agent、结构化输出、置信度、警告、澄清问题及 proposal IDs，但不保留消息原文。只有 `awaiting_review` 状态会包含经过后端校验的 proposal，仍不表示已写入业务表。

班级 onboarding 只能由网页创建和修改。文件经无历史的 OpenClaw extraction turn 全量替换目标列表，人工修改结构化表格后不再经过模型。最终确认在一个事务中创建班级、从课表归纳的科目、学生、节次、基础课表和 agent binding 记录；随后以可重试的外部流程创建 OpenClaw agent、微信登录与 route binding。低配置部署使用一个 Uvicorn worker。SQLite 使用 WAL、外键和 5 秒 busy timeout。

已有班级的课表和座位文件导入遵循“模型只提取预览，网页核对后调用固定领域接口保存”。值日不经过模型，按静态规则生成完整预览后整体确认。课表文件应用在单事务中更新识别到的节次并替换基础课表；座位文件只返回已映射真实学生的矩阵，保存时仍走座位快照校验。
